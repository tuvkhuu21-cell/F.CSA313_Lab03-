## 3. SLO хүснэгт

| Сценарио | SLI | Босго | Цонх |
|---|---|---|---|
| Performance cart | /cart/add latency | p95 < 50 мс | 20 VU, 1 минут |
| Reliability | /pay error rate | < 8% | 20 VU, 1 минут |
| Availability | Амжилттай checks | > 90% | 20 VU, 2 минут |
| Performance report | /report latency | p95 < 450 мс | 20 VU, 1 минут |

### Босго сонгосон үндэслэл

Cart API-д зориудын хүлээлт байхгүй тул 50 мс сонгосон. Pay API ойролцоогоор 5% алдаа гаргадаг учраас 8%-ийн босго тавьсан. Серверийн зогсолтын үед availability 90%-иас дээш байх зорилт тавьсан. Report API-ийн 200–400 мс хүлээлтэд тохируулан 450 мс сонгосон.

### Error budget

2 минут = 120 секунд. Availability SLO = 90%.

120 × (1 − 0.90) = **12 секунд**.

Хүсэлтээр тооцсон error budget-ийг Chaos тестийн дараа бодит гаралтаас гаргана.

## 4. Туршилтын үр дүн


### 4.1 PASS тест

20 VU ачааллаар 1 минутын турш k6 тест ажиллуулахад дөрвөн босго бүгд хангагдсан.

| Үзүүлэлт | Босго | Үр дүн | Төлөв |
|---|---|---|---|
| /cart/add p95 | < 50 мс | 3.81 мс | PASS |
| /report p95 | < 450 мс | 392.29 мс | PASS |
| /pay error rate | < 8% | 3.99% | PASS |
| Checks success | > 90% | 98.66% | PASS |

Нийт 2781 HTTP хүсэлт илгээж, 2744 шалгалт амжилттай, 37 шалгалт амжилтгүй болсон. Төлбөрийн API-д зориуд оруулсан алдаа илэрсэн боловч тогтоосон босгыг хэтрээгүй.

Туршилтын бүрэн гаралт: `results/pass.txt`.

### 4.2 Chaos тест

20 VU, 2 минутын турш серверийг түр зогсоож, дахин асаан шалгасан.

| Үзүүлэлт | Босго | Үр дүн | Төлөв |
|---|---|---|---|
| /cart/add p95 | < 50 мс | 3.56 мс | PASS |
| /report p95 | < 450 мс | 391.46 мс | PASS |
| /pay error rate | < 8% | 20.62% | FAIL |
| Checks success | > 90% | 82.29% | FAIL |

Нийт 5760 хүсэлтээс 4740 нь амжилттай, 1020 нь амжилтгүй болсон.

Availability = 4740 / 5760 × 100 = 82.29%.

Хүсэлтээр тооцсон error budget:
5760 × 10% = 576 хүсэлт.

Бодит алдаа 1020 байсан тул зөвшөөрөгдөх хэмжээг 444 хүсэлтээр хэтрүүлсэн.

Цагаар тооцсон error budget нь 12 секунд. Харин сервер зогссон үед хүсэлтүүд хурдан алдаа буцаадаг тул цагаар болон хүсэлтээр тооцсон үзүүлэлтүүд ялгаатай гарсан.

Серверийн тасалдлаас болж /pay хүсэлтүүд мөн амжилтгүй болсон. Иймээс reliability босго давхар зөрчигдсөн. Серверийн хүртээмжийг төлбөрийн үйлдлийн алдаанаас тусад нь үнэлэхийн тулд health check болон алдааны шалтгааныг тусад нь хэмжих шаардлагатай.

Энэ тестээр сервер дахин ассаны дараах сэргэлтийн хугацааг тусгайлан хэмжээгүй.

Бүрэн гаралт: `results/chaos.txt`.

### 4.3 Зориуд FAIL болгосон тест

/report endpoint-ийн p95 босгыг 450 мс-ээс 100 мс болгон өөрчилж, 20 VU ачааллаар 1 минут шалгасан.

| Үзүүлэлт | Босго | Үр дүн | Төлөв |
|---|---|---|---|
| /cart/add p95 | < 50 мс | 3.39 мс | PASS |
| /report p95 | < 100 мс | 393.13 мс | FAIL |
| /pay error rate | < 8% | 5.83% | PASS |
| Checks success | > 90% | 98.05% | PASS |

/report endpoint-ийн p95 нь 393.13 мс байсан тул 100 мс-ийн босгыг хангаагүй.

k6-ийн exit code 99 гарсан. Энэ нь босго зөрчигдсөнийг CI системд мэдэгдэх боломжтойг харуулсан.

Бүрэн гаралт: `results/fail.txt`.
Скрипт: `slo-test-fail.js`.

## 5. Дүгнэлт

Энэ лабораторид чанарын сценариог SLO болон k6 threshold болгон шалгалаа.
Эхлээд гүйцэтгэл, найдвартай байдал, хүртээмжийн сценарио боловсруулсан.
Хэмжүүр тус бүрд тоон босго сонгох нь хамгийн их анхаарал шаардсан.
PASS тестээр дөрвөн босго бүгд хангагдсан.
Chaos туршилтаар серверийн зогсолт хүсэлтийн амжилтын хувийг 82.29% болгон бууруулсан.
Мөн төлбөрийн API-ийн алдааны хувь 20.62% болж өссөн.
Энэ үр дүн цагаар болон хүсэлтээр тооцсон error budget өөр байж болохыг харуулсан.
FAIL тестээр /report-ийн босгыг зориуд бууруулахад k6 exit code 99 буцаасан.
Ингэснээр сценарио, SLO, threshold гурав хоорондоо хэрхэн холбогддогийг бодит туршилтаар ойлгосон.
